IMPORTANT RULES:

1. Extract only information supported by the project brief.

2. Do NOT invent technologies, features, databases, APIs, architectures, budgets, timelines, or other project details that are not stated.

2b. Extract atomic, discrete requirements. If a brief mentions multiple distinct features, outputs, or deliverables in one sentence (for example, "display employee info, project assignments, and work hours"), split each into an individual requirement item rather than combining them into a single compound requirement.

3. If a requirement is a reasonable interpretation of the brief but is not explicitly stated, you may include it with:
   "confirmed": false

4. Every requirement must include a source_quote.

   * For confirmed requirements, use the exact text that supports the requirement.
   * Do not fabricate source quotes.
   * If there is no supporting text, do not include the requirement.

5. Priority must be based only on information in the brief:

   * "high" = explicitly critical, mandatory, essential, or clearly central to the project
   * "medium" = important but not explicitly critical
   * "low" = optional, secondary, or less important

6. Do not assume that a requirement is high priority merely because it sounds technically important.

7. missing_information should contain only information that would materially improve project understanding or affect:

   * scope
   * implementation
   * architecture
   * integrations
   * timeline
   * budget
   * deployment
   * testing

8. Do not create unnecessary clarification questions for minor details.

9. scope_constraints should contain only constraints explicitly stated or clearly supported by the brief.

10. confidence must be a number between 0.0 and 1.0.

11. Confidence reflects goal and requirement clarity, NOT completeness of business details. Standard actionable briefs should have confidence between 0.80 and 0.95 even if normal operational or business questions remain. Missing details belong in missing_information. Only lower confidence below 0.60 when the project goals are fundamentally unclear, contradictory, or unfeasible.

12. If the brief is extremely vague, purely contradictory, placeholder text (e.g. Lorem ipsum), or lacks concrete functional specifications (for example, "Build me an app", "we need help with machine learning", "build something cool"), return an empty requirements array: "requirements": [] and list the needed clarifications in missing_information.

13. Do not use confidence to compensate for missing information. A response can be valid JSON while still having low confidence if the brief itself was vague.

14. Preserve the client's terminology and intent. Do not redesign or improve the requested solution.

15. Return valid JSON only.

* No markdown
* No code fences
* No explanations
* No text before or after the JSON
